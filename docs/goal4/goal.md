# Goal4: i-PROデータ収集 ローカル管理GUI

## 0. この指示書の目的

既存の `dashboard_test_for_ipro`（Next.js / TypeScript / Yarn）に、ローカルで操作する管理画面を実装する。Goal1〜Goal3-Bで実機検証済みの **カメラ通信、解析、D1へのbackfill/sync、R2サムネイル更新** を再利用し、CLIを手入力せずに操作・進捗確認・結果確認できるようにする。

**今回の対象は収集アプリの管理GUI。** 来店人数・ヒートマップの分析ダッシュボードは別リポジトリ `sample_dashboard` で実装するGoal5であり、混在させない。

本指示書とローカル実装に差がある場合、**ローカル最新コードの公開API・引数・型を先に調査**し、差異を報告してから最小限の互換変更を加えること。GitHubのリモートmainが古い可能性があるため、ローカルのGoal1〜3-B実装を優先する。既存コードやテストを無闇に置き換えない。

## 1. 前提・現在の稼働状況

- カメラは `food` / `island` の2台。既存の認証情報・IP設定は `.env.local` にある。GUIにパスワード編集機能は作らず、秘密値はサーバーのみに保持する。
- `food`: 現行の履歴保存対象は `linecross` のみ。ヒートマップ取得・解析能力は既存共通コードから削除しない。`IPRO_FOOD_HISTORY_KINDS` 等の既存設定を尊重する。
- `island`: 現行の履歴保存対象は `linecross`、`heatmap_mov`、`heatmap_loi`。
- どちらも現行の保存間隔は1時間。正規化された `interval_minutes` は維持し、将来の15分設定を破壊しない。
- Goal3-A: 実D1に `cameras`、`camera_lines`、`linecross_hourly`、`heatmaps_hourly` を作成済み。`yarn d1:import` 再実行で insert/update 0、実機 `yarn sync` で未確定ラインの更新を確認済み。
- Goal3-B: 両カメラの `movcnt:latest` からJPEG取得に成功し、R2の固定キー `cameras/food/thumbnail.jpg` / `cameras/island/thumbnail.jpg` への実アップロードを確認済み。サービス `refreshCameraThumbnail` を再利用する。画像は手動でのみ更新。
- 2026-11-11の `food` の欠測は、別実験で魚眼から1画PTZへ切り替えAI-VMDが無効だったことによる想定。**欠測を0人に変換しない。**
- `runtime/goal1`, `runtime/goal2`, `runtime/goal3-b` に原本・出力がある。原本は不変のままとする。
- 既存の `yarn test` 35件、`yarn lint`、`yarn tsc --noEmit` がGoal3-B終了時点で成功している。回帰を維持する。

## 2. 完了の定義

ブラウザでローカル管理画面を開き、(a) カメラごとの設定・状態を確認、(b) `sync`、(c) 必要時の `backfill`、(d) 各カメラのR2サムネイル更新、(e) 実行結果・ログ確認、を安全に行える。長い処理中もページが応答し、ページをリロードしても実行状態を確認できる。実行は明示的な操作時のみ。バックグラウンド定期ポーリングによるカメラ通信は行わない。

## 3. UI/UX 要件

### 3.1 管理画面 (`/` もしくは `/admin`)

既存Next.js App Routerの画面として実装。既存のCGIテスト画面は壊さず、必要なら管理画面へのリンクを設ける。

**上部：全体状況**
- アプリ名「i-PRO データ収集管理」、ローカル動作であること、接続先別の設定状態（カメラ / D1 / R2）を表示。
- D1 / R2 / VPNの実接続確認を自動実行して見せる場合は、明示的な「接続確認」操作に限定する。単に環境変数がある場合は「設定済み」であり「接続成功」とは書かない。
- `sync` を主要操作として目立たせる。操作対象は `all` / `food` / `island` から選択できるようにし、実装済みCLI・サービスの対応範囲を先に確認すること。

**カメラカード（2台）**
- 名称、内部ID、対象種別（設定から取得し、固定表示にしない）、前回の実行結果・実行時刻を表示。
- R2の既存サムネイル表示。存在しない場合はプレースホルダー。画像の縦横比固定でレイアウトシフト防止。
- 「画像を更新」で `refreshCameraThumbnail` を明示実行。実行中のローディング、成功/失敗、更新時刻、アップロード済み/同一のため省略/結果不明 (`uncertain`) を区別して表示。
- 最終計測日時・保存行数の表示は、**既存スキーマ・SQLを調査した上で取得可能なものだけ**表示する。時刻の種類（最終同期実行時刻、最新の計測区間、画像更新時刻）を混同しない。欠測を0と表示しない。

**履歴取得パネル（補助操作）**
- `backfill` の対象カメラと期間（任意の開始/終了日付、JST表記）を指定できる。期間省略時は実機が保持する取得可能範囲を遡ることを明示する。
- 初回実行・大きな期間の処理は確認操作を挟む。可能なら `--dry-run` の結果を事前表示し、対象範囲・区間・推定件数を確認してから本実行する。
- 読み取り可能なカメラ履歴やAPI呼び出しが必要な計画表示は実際のdry-runの結果を使い、根拠のない件数・時間見積もりを出さない。
- `d1:import`（既取得・正規化済みデータのD1再投入）は「詳細操作」に置くか、当面はCLIのままでもよい。その場合は画面に「保存済みデータの再投入はCLI」と明示する。

**実行履歴・ログ**
- 状態 `queued/running/succeeded/failed/interrupted` を区別し、開始・終了時刻、カメラ、操作種別、期間、結果（inserted/updated/unchanged/no_data/failed/uncertainなど、実際に取得できる項目）を表示。
- 実行中は1〜2秒程度の間隔でジョブ状態をポーリング。ログの増分表示、スクロール追従のON/OFF、コピー機能があると望ましい。
- ログに認証情報や内部ネットワークの機密を出さない。サーバー側でもレダクションする。
- ページをリロードしても実行中ジョブ・直近の実行履歴が復元される。
- エラー時は簡潔な原因と、再試行できる操作を提供する。`uncertain` は成功とも失敗とも断定しない。

### 3.2 体験設計

- 運用者が迷わないよう基本操作は「最新データを同期」「履歴を取得」「画像を更新」「実行履歴」の4系統に限定。
- `sync` と `backfill` を明確に区別。後者をページ表示時に自動開始しない。
- 同時実行防止。二重クリック、複数タブ、別APIリクエストからの重複起動でも二重ジョブにならない。
- 画面幅が狭くても最低限操作できる。入力とボタンは明確なラベルを付け、操作中は状態を通知する。
- D1の時刻は保存上UTCのまま維持し、画面表示のみ原則JSTに変換。「11/21 09:00 JST」のようにタイムゾーンを明示。

## 4. アーキテクチャ

```text
Browser (localhost / forwarded private port)
    |
    | same-origin HTTP
    v
Next.js App Router UI + Node.js Route Handlers
    |
    +-- read-only: camera settings, D1 status, R2 thumbnail (server-side)
    |
    +-- start job -> Local job runner -> Existing Goal3-A/3-B services or CLI
                              |
                              +-- i-PRO CGI via VPN
                              +-- Cloudflare D1 REST API
                              +-- Cloudflare R2 S3 API
                              +-- runtime/goal4/jobs/ (status/log)
```

- Node.jsランタイムに固定する（`export const runtime = 'nodejs'` が必要なRoute Handler）。Edge RuntimeにファイルIO、子プロセス、秘密情報を持ち込まない。
- **既存の `src/collector` の実装を使う。** Next.js UIからCGIパーサー、D1 SQL、R2 PUTを重複実装しない。
- 可能なら既存公開サービス関数を直接呼ぶアダプターを作る。長時間処理については、**HTTPリクエスト内で処理完了を待たず**、独立したジョブランナーへ起動を委譲する。
- 推奨構成は安全な引数配列によるNode.js子プロセス起動 (`spawn`, `shell:false`) + ステータスファイル。子プロセスを起動後、HTTP POSTは `202 Accepted` と `jobId` を速やかに返す。`exec` の出力バッファに大量ログを溜めない。
- Next.jsの開発時HMRやブラウザリロードによってジョブが重複起動しないよう、実行状態の真実はコンポーネントstateではなくサーバー側のジョブ管理へ置く。
- `runtime/goal4/jobs/<jobId>.json` と `<jobId>.log` などをGit管理対象外に保存する。ジョブ記録の作成・更新は原子的に行い、失敗時にもログと終了コードを残す。
- 最初は**アプリ全体で同時に1ジョブ**の単純な排他制御を採用してよい（画像更新も含む）。ファイル作成の排他など原子的手段を利用し、単なるメモリ上のbooleanに頼らない。プロセスが死んだ場合にロックが残り続けない回復手順を持つ。
- サーバー再起動で実行中のジョブが終了した場合は `interrupted` とし、成功にしない。まだ実行中ならその状態を追跡できる設計が望ましい。安全な停止・取消を作れないなら「キャンセル」ボタンは設置しない。
- 既存CLIの出力形式に過度に依存してサマリーを推測しない。必要ならCLIに機械可読のイベント/結果JSONを追加する（既存人間向けログは維持）。

### 4.1 API案（必須の名前ではなく契約例）

| Method / Path | 役割 |
| --- | --- |
| `GET /api/collector/status` | カメラ・D1・R2の設定状態、現在のジョブ、取得可能な非機密概要 |
| `POST /api/collector/jobs` | `sync` / `backfill` / `thumbnail` のジョブ作成。事前検証、排他制御、jobId返却 |
| `GET /api/collector/jobs` | 直近のジョブ一覧 |
| `GET /api/collector/jobs/:id` | ステータス・集計結果・必要範囲のログ |
| `GET /api/collector/thumbnails/:camera` | 非公開R2からサーバー経由でJPEGを返す。`food` / `island` を厳格に制限 |

POST例（送信形式は実装時にバリデーションする）:

```json
{ "operation": "sync", "camera": "all" }
```

```json
{ "operation": "backfill", "camera": "food", "from": "2026-11-01", "to": "2026-11-22", "dryRun": true }
```

```json
{ "operation": "thumbnail", "camera": "island" }
```

- `from/to` はユーザー入力でJSTの日付（暦日）として解釈し、CLI/サービスの時刻契約に従ってUTC等へ変換する。片方だけ指定、逆転、無効日付、未来日、上限超過、未対応カメラ等は明示的に拒否する。制限は既存CLI契約に合わせる。
- `sync --camera ...` 等の実装状況は現行CLIで確認し、未対応ならUIに架空の選択肢を見せない。必要な最小のパラメータ対応を追加する場合はテストを付ける。
- `POST /jobs` は短時間で受理応答し、同期・履歴取得完了を待たない。現在実行中のジョブがある場合は、既存jobIdまたは競合レスポンス（例 `409`）を返し、UIに状態を示す。
- ジョブ履歴は取得数・ログサイズに上限を設け、サイズの大きいログ全体を毎秒返さない。

### 4.2 R2画像の読取り

- 既存のR2バケットは非公開を維持。R2 S3 SDKの `GetObject` をサーバー側で実行するか、認証済みの短期署名付きGET URLを利用。ただしローカルGUIでは**サーバーサイドの画像プロキシ**を第一候補にする。
- キーは `cameras/${validatedCameraId}/thumbnail.jpg` の固定対応のみ。任意オブジェクトキーをクライアントに指定させない。
- `Content-Type: image/jpeg`, 適切な `Cache-Control` を設定し、更新操作直後は新画像が表示される。キャッシュの扱いはHTTPヘッダーとクライアントの明示的再読込で整合させる。
- R2未設定 / 404 / 認証失敗時もページ全体を落とさず、カメラカードで情報を表示。画像バイナリや秘密値をログに書かない。
- サムネイルの撮影/計測時間とR2更新時刻は別物として表示。推測したライブ時刻を表示しない。

## 5. セキュリティ・運用条件

- 想定環境はユーザーのローカルPC・devcontainer、VPNはホスト接続。サーバー側のみCGI/D1/R2へアクセス。**ブラウザへカメラ認証、Cloudflare APIトークン、S3秘密キーを返さない。** `NEXT_PUBLIC_` に秘密値を置かない。
- 管理GUIは認証のない公開Webサービスとしてデプロイしない。外部公開・パブリックなポート転送・トンネルは禁止または追加認証の設計を要する。devcontainerポート転送はPrivateにし、Origin/Host確認やCSRF対策を行う。ローカルアクセスだけだからという理由で無検証のPOSTを許可しない。
- UIから任意のコマンド・任意のCGIパラメータ・任意パスを受け取らない。操作種別とカメラIDはallowlistに限定し、子プロセスは `shell:false` で引数配列を渡す。
- アプリ起動や画面表示だけではカメラへの通信、D1書込、R2上書きは発生しない。サムネイル表示のためのR2 GETは可（再取得によるカメラアクセスは禁止）。
- オペレーションに失敗した場合でもGoal1原本・Goal2正規化出力・D1/R2の既存データを不用意に削除しない。

## 6. テスト計画

### 6.1 自動テスト

1. カメラallowlistと操作入力（不正日付・不正型・任意パス・shell引数注入など）を拒否。
2. ジョブ生成、状態遷移、進捗、最終状態、ログ保存・ページ再取得。
3. ダブルクリック・複数リクエスト時にジョブは1件のみ、排他が働く。
4. プロセスが異常終了・サーバーが再起動した時、成功を偽装せず `failed` / `interrupted` になる。
5. D1/R2の設定不足、VPN不通、No Data、通信エラー、R2 `uncertain` を画面とログで識別する。
6. R2画像をサーバー経由で取得可能。404/権限エラー時はプレースホルダー。API資格情報をレスポンス・ログに含めない。
7. 画面表示・ステータスの定期取得だけでは CGI / D1の書込 / R2 PUT が起動しない。画像を更新しない。
8. Goal1〜3-Bの既存35テストがすべて成功する。
9. `yarn lint` と `yarn tsc --noEmit` を通過する。

### 6.2 手動受け入れ検証（実機 / 実Cloudflare）

1. `yarn dev` で管理画面にアクセスでき、2台のカメラが表示される。既存のCGIテスト画面も維持。
2. カメラ別の履歴種別は現在の設定どおり `food=linecross` / `island=linecross,heatmap_mov,heatmap_loi`。
3. `sync` 実行で実機からD1まで処理成功。途中経過・成功・結果件数を表示し、実行後もページが操作可能。
4. `backfill --dry-run` で期間と対象を確認し、選択した短い履歴範囲を実際に保存。既存レコードが不必要に増えない。
5. 両カメラの既存R2画像を表示。各カメラの「画像を更新」で取得・上書きし、更新後に画像の再表示と日時が正しく変わる。
6. 実行中にページ再読込してもジョブ状態が復元され、二重実行できない。
7. カメラ不通等の失敗を模擬し、分かりやすいエラーと再試行操作が表示される。
8. `d1:import`, `backfill`, `sync`, `r2:thumbnail` のCLIの既存動作が維持されている。
9. D1の4テーブルとR2の固定キーがGUI実装前後で不必要に変更・削除されない。

## 7. 推奨実装順

1. ローカルの `src/collector` と既存CLIの引数・戻り型を調査し、Goal4アダプターの呼び出し方針を決定。画面だけを先にモックで完成したことにしない。
2. ジョブ管理の永続ステータス、排他、エラーと回復の仕組みを作る。
3. Node.js Route Handlerを作り、契約・バリデーション・秘密値マスキングをテスト。
4. D1/R2の読取り専用ステータスとサムネイルプロキシを作る。
5. カメラカード、同期操作、バックフィル期間指定、ジョブ履歴・進捗の順でGUIを実装。
6. モック環境で操作・リロード・二重実行・失敗を確認し、実機で短いバックフィル/同期/画像更新を検証。
7. `README.md` に `yarn dev` 起動手順、devcontainerのポート公開注意点、各ボタンの動作、トラブルシューティングを追記。

## 8. Goal4でやらないこと

- `sample_dashboard` 側のD1参照・グラフ実装（Goal5）。
- 画像の自動定期更新、カメラストリーミング動画、スケジュール実行。
- 多ユーザー権限管理、外部公開Web管理画面、汎用ジョブキュー基盤。
- カメラのIP・認証情報をブラウザから編集する機能。
- D1やR2のスキーマ変更（必須なら理由と移行案を提示してから）。
- 取得済み生ファイルの自動削除・ローテーション。
